# Spec Draft: JSC-109

## Source

- Issue Key: JSC-109
- Title: 3. Support message internationalization
- Description: No description was provided in Jira.

## Goal

Localize user-visible messages and four approved debug messages in `jscov-agent` and `parasoft-istanbul-lib-instrument` for English and Simplified Chinese.

## In Scope

- Localize user-visible CLI/UI prompts, warnings, and errors in `integration/jscov-agent`.
- Localize the Agent initialization banner and lifecycle-failure messages introduced by its logging implementation.
- Localize user-visible load notices, warnings, and errors in `integration/parasoft-istanbul-lib-instrument`.
- Localize the four approved debug messages in `parasoft-istanbul-lib-instrument/src/static-coverage.js` and `src/project-path-mapper.js`, while retaining their `debug` namespace, enablement, and control flow.
- Provide version-controlled, package-local `src/locales/en.json` and `src/locales/zh.json` resources in each project.
- Use `i18next@21.10.0` directly in both projects. This version is MIT-licensed and preserves the instrumentation package's declared Node 10 compatibility.
- Resolve the system locale once, during root-level i18n-module initialization, with `Intl.DateTimeFormat().resolvedOptions().locale`; select `zh` for Chinese locales and `en` otherwise.
- Use i18next's English fallback when a selected-locale translation is unavailable.
- Use i18next named interpolation without pluralization support.

## Out of Scope

- Debug output, internal logs, raw underlying exception details, and structured log prefixes, except for the four approved debug messages in `parasoft-istanbul-lib-instrument/src/static-coverage.js` and `src/project-path-mapper.js`.
- Locales other than `en` and `zh`.
- Locale-aware plural rules.
- Locale environment-variable precedence or overrides (`LC_ALL`, `LC_MESSAGES`, and `LANG`).
- External localization services and i18next backends; JSON resources are bundled or required locally.
- New automated-test coverage for the approved Instrument debug-message localization.

## Behavior

- Each project owns a root-level i18n module (`src/i18n.ts` or `src/i18n.js`) that statically imports or requires the package-local JSON catalogs, maps the system locale to `en` or `zh` once during module initialization, and configures an isolated i18next instance with both resources.
- The i18n module directly exports its i18next instance. Application code obtains user-visible text as `i18n.t('message_key', values)` rather than embedding translated strings at each call site. Catalog placeholders use i18next syntax such as `{{path}}` and `{{port}}`.
- `jscov-agent` applies localized templates to configuration errors, its initialization banner, and fixed lifecycle-failure prefixes, while preserving paths, ports, and underlying error reasons in the emitted messages. The structured `[JSCOV-AGENT][LEVEL]` prefixes remain unchanged.
- `parasoft-istanbul-lib-instrument` applies localized templates to its user-visible load notice, recoverable warnings, and errors without changing its public exports, error types, or coverage-data contracts.
- `parasoft-istanbul-lib-instrument` obtains the approved debug messages from `i18n.t(key, values)` before passing them to its existing `debug` logger. The warning marker is `[WARNING]` in both locales; the `debug` namespace and enablement, exception fallback behavior, and static-coverage output remain unchanged.
- Unsupported system locales and missing non-English translations fall back to the English message.
- Changing the system locale after the message module has loaded does not switch the process language; each manual locale-validation scenario starts a new process.

## Edge Cases (Optional)

- A Chinese system locale selects `zh`; any other locale selects `en`.
- A missing Chinese key uses its corresponding English message.
- Message templates use i18next named placeholders only; plural forms are not interpreted.

## Done When (Acceptance Criteria)

- [ ] Both projects declare the direct MIT-licensed dependency `i18next@21.10.0` and no longer depend on `string-format` for message rendering.
- [ ] `jscov-agent` contains `src/i18n.ts` and package-local `src/locales/en.json` / `src/locales/zh.json` resources; its i18n module serves in-scope user-visible messages through `i18n.t(key, values)`.
- [ ] `parasoft-istanbul-lib-instrument` contains `src/i18n.js` and package-local `src/locales/en.json` / `src/locales/zh.json` resources; its i18n module serves in-scope user-visible messages through `i18n.t(key, values)`.
- [ ] At i18n-module load time, the locale resolver gets the system locale from `Intl.DateTimeFormat().resolvedOptions().locale`, selects `zh` for Chinese locales, and otherwise selects `en`.
- [ ] Missing selected-locale translations fall back to English, and i18next named placeholders render their provided parameter values.
- [ ] The Agent initialization banner and startup/shutdown failure messages use package-local localization keys, while preserving the structured log prefix and error reasons.
- [ ] The four approved Instrument debug messages use package-local localization keys, retain their dynamic paths and error reasons, retain the `[WARNING]` marker in both locales, and leave all other debug output unchanged.
- [ ] Existing Agent i18n tests cover the newly added Agent message keys; no new automated tests are added for the approved Instrument debug-message localization.
- [ ] Manual validation confirms English selection, Simplified Chinese selection, a missing-translation English fallback, and placeholder substitution in both projects.
