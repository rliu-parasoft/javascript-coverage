# Spec Draft: JSC-111

## Source
- Issue Key: JSC-111
- Title: Log ERROR-level messages to the console even when silentMode is enabled
- Description:
  - Currently, once logging is configured successfully, ERROR-level exceptions are not output to the console when `silentMode` is enabled.
  - Ensure that ERROR-level exceptions are still output to the console when `silentMode` is enabled.

## Goal
Ensure that ERROR-level exceptions remain visible in the console after logging has been configured successfully, even when `silentMode` is enabled.

## In Scope
- Restore console output for ERROR-level exceptions when `silentMode=true` and logging configuration has completed successfully.
- Preserve the existing file-log behavior and the existing non-silent console behavior.
- Add unit and integration coverage for silent-mode ERROR output.

## Out of Scope
- Not explicitly defined in Jira.

## Behavior
- After successful logging configuration, an ERROR-level exception must be emitted to the console even when `silentMode` is enabled.
- When `silentMode=false`, console output remains available for INFO, WARN, and ERROR levels.
- When `silentMode=true`, only ERROR is emitted to the console; INFO, WARN, DEBUG, and the startup banner remain suppressed (inferred).
- Console output continues to use stdout (inferred).
- Console ERROR output contains the formatted error message only; the exception stack remains in the file log (inferred).
- The same ERROR-level exception continues to be written to the configured log file (inferred).
- Errors raised before logging configuration completes keep their existing bootstrap behavior (inferred).

## Design

### Logger routing
- After successful configuration, `LoggerProvider` creates a console logger in both modes.
- The console logger level is `info` when `silentMode=false` and `error` when `silentMode=true`.
- The existing stdout console transport and console formatter remain unchanged.
- The file logger's level, timestamp format, file naming, and stack-trace handling remain unchanged.
- `writeBanner()` continues to suppress the banner when `silentMode=true`.

### Error handling and data flow
1. Existing runtime, REST, startup, and shutdown paths call `LoggerProvider.console.error(message)`.
2. The console logger applies the configured level and writes ERROR messages to stdout in both modes.
3. The same path writes the message to the file logger.
4. When an underlying `Error` is available, its stack is written to the file log and not to the console.

### Alternatives considered
- Creating an ERROR-only console logger in silent mode was selected because it centralizes the policy in `LoggerProvider`, preserves existing call sites, and uses Winston's level filtering.
- Adding a separate `errorConsole` API was not selected because it would require changing and auditing every error call site.
- A custom adapter that selectively delegates only ERROR was not selected because it adds policy code that the logger level already provides.

### Testing strategy
- Unit tests verify silent-mode ERROR output, suppression of non-ERROR output and banner, file retention, message-only console formatting, and unchanged non-silent behavior.
- Integration tests simulate REST server startup failure with `silentMode=true`, verifying stdout output, file output including the stack, and unchanged AUT lifecycle behavior.

## Edge Cases
- Errors raised before logging configuration completes are outside the explicitly described path (inferred).

## Done When (Acceptance Criteria)
- [ ] With logging configured and `silentMode=true`, an ERROR-level exception is present in console output.
- [ ] The same ERROR-level exception continues to be written to the configured log file (inferred).
- [ ] With `silentMode=true`, INFO, WARN, DEBUG, and the startup banner remain absent from console output (inferred).
- [ ] Console output remains on stdout and contains the error message without the exception stack (inferred).
- [ ] With `silentMode=false`, existing INFO/WARN/ERROR console behavior remains unchanged (inferred).
- [ ] Bootstrap errors raised before logging configuration keep their existing output behavior (inferred).
