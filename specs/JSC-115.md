# Spec Draft: JSC-115

## Source

- Issue Key: JSC-115
- Title: Remap the runtime JSON coverage data back to the source code locations
- Description:
  - The current runtime JSON file may contain the `inputSourceMap` property.
  - The `inputSourceMap` property contains source map data. When it is present, the current coverage data is not for the original source code, but for code processed during the build.
  - Refer to the `remapCoverageData(coverageData)` method in `integration\\parasoft-istanbul-lib-instrument\\src\\static-coverage.js`, which uses `inputSourceMap` to map coverage data back to the original source code.
  - Perform the remapping before coverage data is saved to a local file after the REST API `/session/stop` call.
  - The `ts-webpack-bable-loader-express-server` project in `javascript-coverage-samples` can be used for testing.

## Goal

Before runtime coverage data is persisted after `/session/stop`, map coverage locations from processed or generated code back to the original source-code locations using the `inputSourceMap` data when it is available.

## In Scope

- Apply source-map remapping to runtime coverage data before the `/session/stop` flow saves it locally.
- Reuse the remapping behavior represented by `remapCoverageData(coverageData)` in `integration\\parasoft-istanbul-lib-instrument\\src\\static-coverage.js`.
- When `inputSourceMap` is absent, skip remapping and preserve the original runtime coverage data.
- When one generated file maps to multiple source files, preserve the mapped coverage for every source file.
- Validate the behavior with the `ts-webpack-bable-loader-express-server` sample project (inferred).

## Out of Scope

- Not explicitly defined in Jira.

## Behavior

- When persisted runtime coverage contains `inputSourceMap`, its coverage locations correspond to the original source files after remapping.
- Remapping occurs after `/session/stop` obtains the runtime coverage and before the resulting coverage data is written to the local runtime JSON file.
- Runtime coverage without `inputSourceMap` skips remapping and remains persisted as the original coverage data; the file is not discarded.
- If one generated coverage input maps to multiple original source files, the persisted result retains a separate mapped result for every source file (inferred).
- If multiple mapped inputs resolve to the same original source path, their coverage is merged rather than one mapped result overwriting another (inferred).
- Istanbul's transformer applies a source map on a best-effort basis: mapped statements, functions, and branches are retained, while coverage items with no mapping are omitted when at least one item maps (implementation behavior).
- Remapping must not require the application under test to expose an additional API beyond the existing `/session/stop` flow (inferred).

## Edge Cases (Optional)

- A runtime coverage entry has no `inputSourceMap` (inferred).
- A source map cannot be parsed or produces no mapped coverage; the generated coverage is retained and stop continues (implementation decision).
- One source map references multiple original source files; every mapped source result must survive persistence.
- Runtime coverage contains multiple file-coverage entries that require independent remapping (inferred).

## Clarifications

### Assumptions

- [A1] Runtime coverage entries use an Istanbul-compatible file-coverage shape that can be processed using the same source-map remapping semantics as the referenced static-coverage implementation.

### Confirmed Decisions

- [D1] When `inputSourceMap` is absent, abandon the remapping attempt but retain the original runtime coverage data.
- [D2] When one generated file maps to multiple source files, retain all mapped source-file results rather than selecting only one.
- [D3] The pulled stop flow persists the direct `getCoverage()` map, so each file-coverage entry is remapped independently before serialization.
- [D4] Invalid source maps or source maps that produce no mapped coverage use a non-fatal per-file fallback; partially mapped files follow Istanbul's best-effort behavior.
- [D5] Successfully remapped entries omit the consumed `inputSourceMap`; fallback entries retain their original metadata.

### Unclear Points

- [U1] Resolved by the pulled code: `/session/stop` calls `SessionService.stopSession()`, which serializes the direct `getCoverage()` map.
- [U2] Resolved by the pulled code: the stopped session file is a map keyed by coverage path.

### Missing Info

- [M1] Resolved by D4: invalid or wholly unmappable source maps use a non-fatal per-file fallback; partial mappings follow Istanbul's transformer.
- [M2] Resolved by D5: successful remaps omit `inputSourceMap`, while fallback entries retain it.

### Questions for Human

- [Q1] (re [A1]) Resolved: runtime coverage is treated as the Istanbul-compatible file-coverage map used by the referenced remapper.
- [Q2] (re [U1]) Resolved: use the pulled `SessionService.persistSessionCoverage()` stop boundary.
- [Q3] (re [U2]) Resolved: remap each entry in the direct coverage map and retain every source-file result; duplicate mapped paths are merged.
- [Q4] (re [M1]) Resolved: preserve generated-code coverage per file and continue the stop request, matching the existing static writer's non-fatal behavior.
- [Q5] (re [M2]) Resolved: omit `inputSourceMap` from successfully remapped entries and retain it on fallback entries.

### Risks

- [R1] (re [U1]) Without a defined stop-session persistence boundary, the remapping could be implemented in the wrong layer or applied after the JSON has already been written.
- [R2] (re [U2]) An incorrect assumption about the runtime JSON shape could remap only part of the coverage or corrupt the session file structure.
- [R3] (re [M1]) Strict failure versus fallback changes whether a malformed source map loses an entire runtime result or produces a less precise generated-code result.
- [R4] (re [M2]) Retaining or removing `inputSourceMap` changes the persisted data contract and may affect downstream consumers.
