# Spec Draft: JSC-118

## Source
- Issue Key: JSC-118
- Title: Minify the build artifacts in the production environment
- Description:
  - Our current build artifacts contain source code information.
  - A minification step is required to remove information such as variable names and method names from the source code and reduce the size of the build artifacts.
  - When implementing this task, both production and development environments need to be taken into consideration.
  - Minification is only required in the production environment.

## Goal
Produce a production `jscov-agent` bundle that is minified, obscures implementation identifiers, and does not expose source maps or known generated source metadata, while keeping the local development build unminified.

## In Scope
- Add a minification step to the production build artifacts.
- Account for both production and development environments when implementing the build behavior.
- Remove source maps and known generated source metadata from production artifacts; minification obscures implementation identifiers such as local variable and method names.
- Reduce the size of production build artifacts through minification.
- Use the Vite build mode as the environment flag: production is the default, while development mode is explicitly selected for local work.
- Produce the production `jscov-agent` bundle in `dist/agent.js` and package only that file in the release ZIP under `integration/jscov-agent/`.
- Keep the development bundle in `dist-dev/agent.js` and do not apply production-only minification or source-information removal to it.

## Out of Scope
- `integration/parasoft-istanbul-lib-instrument`'s npm tarball.
- Other distribution artifacts outside `jscov-agent`.

## Behavior
- Production build artifacts are minified before they are produced or packaged.
- The production bundle is minified with Vite's built-in Oxc minifier; production source maps and known bundler source metadata are removed.
- Production artifacts do not expose source maps or known generated source metadata.
- Minification reduces the size of production build artifacts.
- Removing sensitive source information is the primary acceptance focus; no numeric artifact-size target is required.
- Minification is only required in the production environment.
- Development artifacts remain unminified; production-only minification must not be applied to development builds.
- Development builds may emit sourcemaps for local debugging; these files are not used by the unchanged Gradle release path.
- The existing `npm run build` script remains the build entry point; without an explicit mode it uses the secure production defaults.
- A local developer can select development mode with `npm run build -- --mode development`, which writes the unminified `dist-dev/agent.js` output.
- Production mode writes `dist/agent.js`; the Gradle distribution flow consumes this unchanged default output without production-specific configuration.

## Design

### Environment Selection
- The Vite `mode` flag selects the build environment.
- An unspecified mode defaults to `production`.
- Only an explicit `--mode development` enables the local, unminified development build.
- Production mode enables the Vite built-in minifier and disables source-map generation.

### Build and Packaging Flow
- `npm run build` remains the existing npm entry point and produces the production bundle by default.
- `npm run build -- --mode development` produces the local development bundle without production-only minification.
- The production bundle is written to `dist/agent.js`; the development bundle is written to `dist-dev/agent.js`.
- Gradle's unchanged `assembleIntegrationDist` copies only `dist/agent.js` together with `resources/agent.jsonc` into the integration distribution staging directory.
- The root `distribution` task packages the staged production agent under `integration/jscov-agent/` in the release ZIP.
- Gradle keeps a generic internal build-and-package path; production mode is selected by the npm/Vite default rather than by a production-specific Gradle task or explicit Gradle mode flag.

### Failure and Isolation Behavior
- `dist` is cleared before a production build so an earlier artifact cannot be reused after a failed build.
- A production build failure prevents release packaging; source-metadata validation is performed by the npm test and evidence-verification paths, and no unminified fallback is allowed.
- Development output and production output use separate directories so local builds cannot overwrite the release candidate.
- Runtime agent behavior and user-facing messages remain unchanged.

### Verification Strategy
- Development-mode verification confirms that `dist-dev/agent.js` remains available and unminified.
- Production-mode verification confirms that `dist/agent.js` is generated, contains no `.map` output or `sourceMappingURL`, and contains no bundler source-path or build-region comments.
- Existing agent runtime tests run against the production bundle to verify startup, configuration parsing, HTTP behavior, and session lifecycle.
- Distribution verification confirms the release ZIP contains only the production `jscov-agent` bundle and excludes the development bundle.
- No numeric artifact-size threshold is asserted; size reduction is recorded as a consequence of minification, while removal of sensitive source information is the primary gate.
- The source-metadata scan covers source maps, `sourceMappingURL`, and known bundler region markers; it is not a general secret scanner for credentials, tokens, or internal URLs.

## Edge Cases (Optional)
- A development build must not accidentally receive production-only minification behavior.
- Production artifact generation must remain usable after source identifiers are transformed.

## Done When (Acceptance Criteria)
- [x] Production build artifacts include a minification step.
- [x] Production artifacts are minified and do not expose source maps, `sourceMappingURL`, or known bundler source metadata; this acceptance check does not claim to be a general secret scan.
- [x] The production build applies minification and removes sensitive source information; no numeric size-reduction threshold is required.
- [x] Development artifacts remain unminified; the production-only minification step does not alter development builds.
- [x] The default build path produces the production bundle, while `--mode development` is required for the local unminified build.
- [x] Both production and development environments have been considered in the implementation and validation.
- [x] `dist/agent.js` is the only `jscov-agent` bundle packaged in the release ZIP; the development `dist-dev/agent.js` and instrumentation `.tgz` are excluded.
- [x] The production bundle passes the existing agent runtime tests.

## Clarifications

### Assumptions
- [A1] “Source code information” includes at least variable names and method names, as stated in the Jira description; treatment of source maps or other metadata is not specified. → **Resolved:** Production minification obscures implementation identifiers, and production artifacts must not expose source maps or known generated source metadata. This acceptance scope is not a general secret scan.

### Unclear Points
- [U1] The expected development-environment behavior is unclear: Jira says it must be considered but does not state whether development artifacts must remain unminified or may optionally be minified. → **Resolved:** Development artifacts remain unminified; minification is limited to production builds.
- [U2] The required meaning of “reduce the size” is unclear because no size target or comparison method is provided. → **Resolved:** Sensitive-information removal is the primary acceptance focus; no numeric artifact-size threshold is required, and size reduction is verified as a consequence of applying minification.

### Missing Info
- [M1] Jira does not identify the build command, build configuration, artifact types, or artifact locations to which the production minification step applies. Repository inspection showed that `integration:jscov-agent` uses `npm run build`/Vite to produce `dist/agent.js` by default and `dist-dev/agent.js` for explicit development mode; `integration:parasoft-istanbul-lib-instrument` separately produces an npm `.tgz` containing `src`, but it was unclear whether that tarball was also in scope. → **Resolved:** Only `jscov-agent` is in scope. The production-mode output is `dist/agent.js` and the copy staged under `integration/jscov-agent/` in the release ZIP; the development `dist-dev/agent.js`, instrumentation `.tgz`, and other artifacts are out of scope.

### Questions for Human
- [Q1] (re [A1]) Should production minification remove or alter source maps and other source-related metadata, or should this task address only variable and method names in the generated code? → **Answered:** Remove source maps and known generated source metadata, while using minification to obscure implementation identifiers. General secret scanning is outside this task's acceptance scope.
- [Q2] (re [U1]) Should development artifacts remain unminified, or should development builds support an optional minification mode while keeping production minification mandatory? → **Answered:** Development artifacts remain unminified; only production builds are minified.
- [Q3] (re [U2]) What measurable size criterion should be used to confirm the reduction—for example, any reduction versus a required percentage or maximum size? → **Answered:** No numeric size criterion is needed; verify that minification is applied and that sensitive source information is removed.
- [Q4] (re [M1]) Should JSC-118 apply only to the `integration:jscov-agent` production outputs (`dist/agent.js` and the packaged `integration/jscov-agent/agent.js`), or should it also cover the `integration:parasoft-istanbul-lib-instrument` npm tarball and other distribution artifacts? → **Answered:** Apply JSC-118 only to `jscov-agent`; its production output is the only agent bundle packaged, while the instrumentation `.tgz`, development output, and other distribution artifacts are out of scope.

### Risks
- [R1] (re [A1]) If source maps or other source metadata are handled differently than expected, production artifacts may still expose source information or debugging workflows may regress.
- [R2] (re [U1]) If development behavior is not agreed, local debugging or development build performance may be affected unexpectedly.
- [R3] (re [U2]) Without a measurable size criterion, the size-reduction requirement may be difficult to verify consistently.
- [R4] (re [M1]) If the in-scope artifacts are not identified, the minification step could be applied to the wrong outputs or omitted from required production outputs.
